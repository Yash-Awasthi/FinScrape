The configured model provider returned HTTP 5xx for every analysis call, so the ingest worker fell back to its heuristic scorer from 2026-11-25 22:10 UTC until 2026-11-26 12:05 UTC, about 14 hours. ## Detection

The signal was `GET /api/health` reporting `heuristic_share_24h` 0.23 with `heuristic_alert:true`, the model-provider-outage detect step in [../INCIDENTS.md](../INCIDENTS.md). It fired on a manual morning check, not on a page: nothing watches the share between checks. The confirming evidence was `AI proxy HTTP 5xx` in the `ingest.yml` log, while the workflow itself still concluded `success`. Time from first bad state to detection was about 11 hours, which is the real finding of this exercise.

## Root cause

The upstream provider answered HTTP 5xx for every chat completion in the window, which is the whole mechanism; the worker's fallback then scored the backlog with heuristics rather than failing the run.

- Upstream cause: provider-side 5xx on the chat completions endpoint, outside this repository's control.
- Local fault: no local fault established in the failure itself. The slow detection is a local gap, recorded under contributing factors.
- Mechanism: each analysis call retried, then wrote a heuristic label, so the run stayed green and the degradation was visible only in aggregate.

## Contributing factors

- Nothing alerts on `heuristic_share_24h`; the number is only read when someone runs `curl` against `/api/health`.
- A degraded run still concludes `success`, so a green Actions list looks healthy.
- The fallback is silent by design: it writes a plausible tag rather than a marker that a reader notices.
- The 24 h share is a lagging measure, so a 14 h window only crosses 0.2 late in the failure.

## What went well

- The fallback kept the pipeline writing instead of dropping events: 96 rows landed where a hard failure would have written none.
- `/api/health` exposed the exact numbers needed, `heuristic_share_24h` and `heuristic_alert`, in one call.
- The playbook was usable as written: detect, confirm, act and reanalyse each mapped to one command.

## What went wrong

- Detection depended on a person looking, about 11 hours after the first 5xx.
- The green workflow conclusion hid the failure from the run list.
- The provider-outage playbook has no step that checks the reanalyse actually re-judged the rows, so "resolved" rests on the health share alone.
